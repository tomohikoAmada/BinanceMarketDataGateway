# 2026-08-23 project handoff

This document is the handoff checkpoint for the Recorder, Contracts, Projection, and Gateway
repositories. It records only completed or directly verified work. A candidate is not called a
formal release, and queued remote CI is not treated as a serial development gate.

## What the system is

The four repositories form one Binance market-data system with deliberately narrow ownership:

```text
Binance public market-data APIs
            |
            v
Gateway: live transport, bootstrap/resync, bounded egress and client-facing gRPC
            |
            +--> Contracts: Protobuf messages and the separate gRPC service artifact
            |
            +--> Projection::ProtoAdapter --> Projection::Core
                                                |
                                                v
                                      deterministic order-book state

Recorder: an independent durable raw-data acquisition/storage system
          (Gateway has no Recorder dependency)
```

The Gateway runtime is intentionally not implemented yet. Its target is a low-latency,
single-writer path for one venue + market + symbol first, with direct reuse of Projection rather
than a second order book, sequence classifier, facade, event bus, DI framework, or plugin system.

## Work that is not complete

### 1. Contracts PR #16 is not push-ready yet

The most recent local release-readiness candidate is clean at:

```text

feat/contracts-release-readiness@9d14a2b3b6b5ab6be332c02e621d92d90d128a3f
```

It is based on the current remote PR #16 candidate `9c34199...` and is deliberately **not pushed**.
It implements clean-source export attestation, frozen lock/profile/graph/list inputs, exact Conan
cache selection, integrity checking, non-overwriting bundle output, and release documentation.
Local evidence is strong: 31 focused tests; 515 passed/9 skipped overall; Ruff; strict mypy on
changed modules; isolated candidate package build and CTest 2/2; and a real 126,917,262-byte cache
bundle restored into a fresh Conan home with an exact `--no-remote --build=never` graph.

Independent review nevertheless found two real P1s:

1. gRPC provenance currently binds its base dependency by coordinate and RREV, but not by the exact
   base package ID and PREV that it linked. A later rebuild under the same base RREV/package ID can
   produce a different PREV; the bundle graph could then select that replacement without the gRPC
   package proving the exact binary relationship.
2. Frozen graph replay compares recipe/full-reference sets and the base/gRPC tuple, but does not
   compare every dependency node's context, settings, options, and multiplicity. A supplied graph
   can therefore misdescribe a third-party node while retaining the same package identity and be
   embedded in the manifest.

There is also a P2 cleanup race: after the bundle hard-link succeeds and the manifest link fails,
an unconditional path unlink could remove a file replaced by another writer in the interval.
Do not push or merge `9d14a2b` until both P1s are closed and independently re-reviewed. Fix the P2
in the same small patch if it does not complicate the release path.

## Agent and GitHub operating rules

- The lead agent owns architecture, cross-repository decisions, complex review, and acceptance.
- Use Luna for simple/medium implementation and **all GitHub mutations**: PR edits, comments,
  ready/merge, issue closure, pushes, and remote branch deletion.
- Use Sol for genuinely exploratory or high-risk work such as Conan provenance/release closure,
  concurrency, protocol/sequence correctness, and independent release review.
- Prefer isolated worktrees/clones for cross-repository work. Never overwrite another agent's or
  the user's dirty worktree.
- Merge completed PRs with merge commits unless explicitly directed otherwise. Delete a branch
  only after the PR is MERGED, `main` is proven to carry the intended tree/content, and the branch
  tip has not moved. Never use `git branch -D` for cleanup.
- Do not wait for slow remote CI. Read failures when they appear, fix real defects, and continue
  independent work. Documentation-only changes do not need CI.
- Use Mac for rapid iteration. Run focused checks first and proportionate full local gates after
  code changes. Preserve final clean-cache/native Ubuntu validation for release/deployment claims.
- Do not invent formal pins, publication, official protocol facts, or test claims. Candidate,
  merged, built, restored, and published are separate states.
- Avoid overdesign and overdefense. Keep dependencies explicit, coupling low, cohesion high, and
  the future Gateway hot path bounded and allocation-conscious.

## Ox Alpha Free assessment

Ox Alpha Free was tried through the interactive OpenCode terminal flow. Its price is attractive,
and it can be useful for a tightly bounded, read-only second opinion or a small local inspection.
In this session it did not provide a sufficiently stable, reproducible end-to-end executor: model
selection/session automation, context retention, completion signaling, and exact evidence handoff
were less predictable than the native Luna sub-agent path. There were not enough clean successful
runs to make a scientific claim that its reasoning quality equals Luna.

For this project, Luna is the better default for bounded implementation and GitHub operations
because it reliably returns the changed scope, exact commit, tests, and remote state inside the
team workflow. Ox Alpha should remain optional and non-authoritative: use it for free read-only
cross-checks with a narrow prompt, then verify its conclusions locally or with the lead/Sol. Do not
make it the sole approver for merges, package provenance, releases, protocol correctness, or branch
deletion unless a later team first demonstrates a stable non-interactive invocation and repeatable
evidence output.
